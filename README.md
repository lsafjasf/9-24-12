# 延迟队列缺陷修复（Python 3，仅标准库）

所有时间推进都是显式的虚拟时钟（`DelayedQueue.now` / `advance(delta)`），
测试中没有任何真实等待，复现条件完全确定。

## 文件

- `delayed_queue_buggy.py` — 现网缺陷版本（保留用于对照复现）
- `delayed_queue.py` — 修复后的实现（索引化二叉最小堆）
- `reproduce.py` — 五类确定性复现场景，可对缺陷版/修复版运行
- `test_delayed_queue.py` — 16 个回归测试（`unittest`，含堆不变量检查）
- `benchmark.py` — 对数复杂度与内存实测
- `RESULTS.md` — 上述命令的固化输出

## 运行命令

```bash
python3 reproduce.py --impl buggy   # 期望：5 个场景全部 BUG，退出码 1
python3 reproduce.py --impl fixed   # 期望：5/5 正确，退出码 0
python3 -m unittest -v test_delayed_queue
python3 benchmark.py
```

## 四类现网问题与根因

1. **取消过的任务仍被执行**：缺陷版用一次性集合标记取消，旧堆条目弹出时
   把标记消费掉，重复调度后的条目因此"复活"；且重调度后旧标记仍在，语义自相矛盾。
   修复版取消即从堆与索引中物理删除（`_remove`），不存在任何复活路径；
   取消后再次 `schedule` 是一个全新条目。
2. **同一到期时刻漏任务**：缺陷版就绪判定是严格 `< now`，恰好等于当前时刻
   的任务全部漏掉。修复版改为 `deadline <= now`，并用单调提交序号
   `seq` 作第二排序键，保证同刻任务严格按提交顺序 FIFO 执行、一个不丢。
3. **时钟推进后顺序错乱**：缺陷版重调度直接原地改写堆节点的 deadline，
   破坏堆不变量。修复版重调度 = 真实删除 + 重新插入（各 O(log n)），
   插入后立即 sift 恢复不变量；回归测试通过 `_assert_invariant` 校验
   `parent <= child` 且索引位置一致。
4. **长期运行内存增长**：缺陷版取消只删字典、堆内死条目永久保留
   （十万次取消堆内残留 100000 条）。修复版堆中只存活条目，
   `internal_size() == pending_count()` 恒成立。

另修复：缺陷版任务在自己回调内重调度自己时，旧节点已弹出但仍留在索引中，
   重调度只更新了死节点，导致周期任务只执行一次。修复版在调用回调前先完成
   摘除，回调内 `schedule(self, ...)` 走正常插入路径，无重复条目也不丢实例。

## 复杂度

设 n 为当前存活任务数：

| 操作 | 复杂度 | 说明 |
| --- | --- | --- |
| `schedule`（新增） | O(log n) | 索引堆上溯 |
| `reschedule`（同 id） | O(log n) | 删除 + 插入，均为 O(log n) |
| `cancel` | O(log n) | 索引定位 O(1) + 堆删除 O(log n)，无墓碑、无扫描 |
| `advance` 取出最早任务 | O(log n) | 取根 O(1) + 下沉 O(log n) |
| 触发 k 个任务 | O(k log n) | 每次触发一个 log 步 |

实测（本机，best-of-5 微秒/操作，节选；完整数据见 `RESULTS.md`）：

| n | 插入 | 取消 | 重调度 |
| --- | --- | --- | --- |
| 2 000 | 0.57 µs | 2.08 µs | 5.56 µs |
| 8 000 | 0.60 µs | 2.51 µs | 5.67 µs |
| 32 000 | 0.67 µs | 3.21 µs | 7.13 µs |
| 64 000 | 0.75 µs | 3.75 µs | 8.49 µs |

n 扩大 32 倍（2k→64k，log2 增加 5），单次插入仅增约 32%、取消约 80%，
符合对数关系；绝无线性扫描。

## 内存证据（10 万次）

- 100 000 次 schedule+cancel 后：`pending_count = 0`，
  内部堆槽位 = 0，索引条目 = 0，GC 存活 `Task` 对象 = 0。
- 固定 500 个真实任务上做 100 000 次 cancel/re-schedule 后：
  存活 = 500、堆槽位 = 500、GC 存活 `Task` 对象 = 500；
  再做 100 000 次仍是 500，`tracemalloc` 当前占用两轮基本不变
  （197.5 KiB → 197.7 KiB），即存活条目数与实际待执行任务数一致且不增长。
